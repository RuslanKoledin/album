# Codex Execution Pack для проекта фотокниг

Этот каталог превращает большое ТЗ в управляемую систему разработки через Codex.

Главная идея: **Codex никогда не получает команду «реализуй всё ТЗ»**. Он получает одну небольшую задачу, ограниченный набор разделов спецификации, список разрешённых изменений, тесты и критерии приёмки.

## 1. Источники истины

Приоритет документов:

1. `AGENTS.md` — обязательные правила работы агента.
2. `tasks/current/*.md` — единственная текущая задача.
3. `docs/spec/MASTER_SPEC.md` — неизменяемое полное ТЗ.
4. `docs/spec/sections/` — автоматически разбитые разделы ТЗ для экономии контекста.
5. `docs/decisions/DECISIONS.md` и ADR — принятые решения по TBD и архитектуре.
6. Код, тесты и миграции.

Если документы противоречат друг другу, Codex обязан остановиться и поставить задаче `BLOCKED`.

## 2. Почему нельзя давать полное ТЗ одной командой

Большая задача создаёт несколько рисков:

- агент теряет малозаметные требования;
- начинает додумывать значения `TBD`;
- одновременно меняет архитектуру, UI, API и данные;
- считает задачу завершённой без полного тестирования;
- исправляет одну часть и ломает другую;
- создаёт слишком большой diff, который невозможно качественно проверить двум владельцам проекта.

Поэтому проект выполняется вертикальными задачами. Одна задача должна давать один проверяемый результат и обычно затрагивать один пользовательский сценарий или один инфраструктурный контракт.

## 3. Статусы задач

| Статус | Кто ставит | Значение |
|---|---|---|
| `BACKLOG` | владельцы | задача описана, но ещё не готова |
| `READY` | владельцы | входные данные и зависимости готовы |
| `IN_PROGRESS` | Codex | агент начал работу |
| `BLOCKED` | Codex или владельцы | работа остановлена из-за решения, ошибки или зависимости |
| `IMPLEMENTED` | Codex | код и тесты готовы, но независимая проверка не выполнена |
| `VERIFIED` | владельцы | тесты и ручная проверка пройдены |
| `DONE` | владельцы | изменения приняты и объединены в основную ветку |
| `CANCELLED` | владельцы | задача отменена осознанно |

**Codex запрещено ставить `VERIFIED` и `DONE`.** Это ваша зона ответственности.

## 4. Рабочий цикл одной задачи

1. Один из вас выбирает следующую задачу без незакрытых зависимостей.
2. Создаёт детальный файл по `tasks/TASK_TEMPLATE.md`.
3. Проверяет Definition of Ready.
4. Копирует или перемещает задачу в `tasks/current/`.
5. Запускает Codex с текстом из `prompts/EXECUTE_TASK.md`.
6. Codex меняет статус на `IN_PROGRESS`, реализует только scope задачи, запускает тесты и заполняет evidence.
7. Codex ставит `IMPLEMENTED`, но не `DONE`.
8. В отдельном новом потоке другой Codex запускается с `prompts/REVIEW_TASK.md` и пытается найти ошибки.
9. Вы вручную запускаете продукт, проходите checklist и проверяете diff.
10. При успехе ставите `VERIFIED`, затем после merge — `DONE`.
11. При ошибках создаёте review report и запускаете `prompts/FIX_TASK.md`.

## 5. Правило двух независимых проверок

Для каждой задачи используются три роли:

- **Builder Codex** — пишет код.
- **Reviewer Codex** — в новом потоке проверяет код, требования и тесты; сначала не вносит изменения.
- **Human reviewer** — один из двух владельцев проекта подтверждает UI, бизнес-логику и итоговый результат.

Не просите тот же поток Codex сначала реализовать, а затем «объективно проверить себя».

## 6. Размер задачи

Хорошая задача:

- имеет один измеримый результат;
- содержит 3–10 acceptance criteria;
- ссылается на конкретные разделы ТЗ и requirement IDs;
- имеет ограниченный список файлов или модулей;
- содержит обязательные автоматические тесты;
- может быть полностью проверена отдельно;
- не требует скрытых бизнес-решений.

Плохая задача:

- «сделай авторизацию, личный кабинет и безопасность»;
- «реализуй редактор как Mixbook»;
- «сделай весь backend»;
- «улучши архитектуру»;
- «закончи всё, что осталось».

## 7. Параллельная работа

Параллельно запускаются только задачи без общих изменяемых контрактов.

Можно параллельно:

- публичная страница и независимый технический spike;
- UI-компоненты и подготовка тестовых fixtures;
- документация API и независимый benchmark.

Нельзя параллельно без предварительной фиксации контрактов:

- миграции одной таблицы;
- BookDocument и renderer;
- API и frontend, если контракт ещё не утверждён;
- цена и checkout;
- approval и order snapshot.

Для параллельных задач используйте разные ветки или worktree.

## 8. Команды проверки task-документов

```bash
python3 scripts/validate_task_docs.py
python3 scripts/status_summary.py
```

Первая команда проверяет обязательные поля, допустимые статусы и наличие acceptance criteria. Вторая строит сводку статусов.

## 9. Первые действия в реальном репозитории

1. Скопировать содержимое этого пакета в корень репозитория.
2. Зафиксировать `MASTER_SPEC.md` отдельным commit.
3. Выбрать технологический стек через ADR, а не случайное решение Codex.
4. Закрыть блокирующие `TBD` для ближайшего этапа.
5. Создать первую детальную задачу `META-001` на scaffold репозитория.
6. Не начинать редактор, AI и оплату до завершения соответствующих spikes и контрактов.

## 10. Что обновляется после каждой задачи

Codex обязан обновить:

- статус и evidence текущей задачи;
- список реально изменённых файлов;
- команды и результаты тестов;
- миграции и API-документацию, если применимо;
- `docs/decisions/DECISIONS.md`, только если решение уже утверждено владельцами;
- `tasks/STATUS.md`.

Codex не должен:

- переписывать `MASTER_SPEC.md`;
- закрывать `TBD` самостоятельно;
- менять соседние функции «заодно»;
- ставить задаче `DONE`;
- скрывать непройденные тесты;
- заменять тесты комментариями или моками без согласования.
