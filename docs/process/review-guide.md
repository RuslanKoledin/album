# Приёмка крупных и рискованных задач

Это усиленный процесс для задач, ошибка в которых может привести к потере
работы пользователя, утечке фотографий, неправильной цене, печати неверного
макета или дорогому возврату. Он не требуется для каждой небольшой правки.

## Когда применять

Расширенная приёмка нужна для:

- auth, session, permissions и ownership;
- upload, private media, retention и удаления;
- `BookDocument`, migrations, autosave и recovery;
- pricing, checkout, orders, payment и refunds;
- preflight, approval, render и production handoff;
- значимого изменения API или пользовательского flow;
- milestone/gate handoff по просьбе владельца продукта.

Для небольшого UI, документации, config или локального рефакторинга достаточно
проверок из соответствующего `AGENTS.md` и engineering rules.

## Роли

- Исполнитель реализует ограниченный scope и предоставляет фактические
  доказательства.
- Независимый reviewer рекомендуется для перечисленных выше рискованных
  областей и сначала проверяет, а не исправляет реализацию.
- Владелец продукта подтверждает бизнес-поведение, тексты и основной flow.
- Production owner подтверждает параметры печати и физический результат.

Один человек может выполнять несколько ролей на раннем этапе, но это
фиксируется явно. Формальная независимая проверка не считается проведённой,
если исполнитель проверял только собственную работу.

## Что предоставляет исполнитель

- краткий результат и границы изменения;
- список изменённых файлов;
- точные команды проверок и их реальные результаты;
- обновлённые contracts/migrations, если они менялись;
- screenshot, видео или PDF для визуального результата, когда это важно;
- известные ограничения и непроверенные внешние зависимости;
- ручные шаги, которые должен пройти владелец.

Не нужно запускать все виды тестов для каждой задачи. Проверка выбирается по
риску и выполняется на самом низком достаточном уровне.

## Ручная проверка

Для применимых сценариев владелец:

1. запускает проект по корневому или локальному README;
2. проходит основной пользовательский путь;
3. проверяет релевантный ошибочный ввод и отказ backend;
4. проверяет повтор действия, refresh, back и восстановление работы;
5. проверяет соседнюю функцию, которую могло затронуть изменение;
6. для UI смотрит релевантные mobile и desktop размеры;
7. сравнивает результат с acceptance criteria и открытыми ограничениями.

Не требуется искусственно демонстрировать loading, empty, offline и другие
состояния, если они не применимы к изменённому сценарию.

## UI и пользовательский flow

Проверяются:

- понятный следующий шаг и отсутствие тупиков;
- сохранение пользовательского выбора при recoverable failure;
- loading/error/retry/offline там, где они действительно возможны;
- keyboard navigation, visible focus, labels, контраст и размеры tap targets;
- отсутствие raw backend errors, placeholder actions и ложных обещаний;
- соответствие мобильной версии заявленному scope.

Mock допустим, если текущий этап явно mock-first, данные помечены как тестовые,
production path не заявлен готовым и существует зафиксированная граница
будущей интеграции.

## API и backend

Для применимого endpoint проверяются:

- нормативный request/response/error contract;
- authentication, authorization и ownership;
- invalid input и стабильный machine-readable error code;
- повтор запроса и idempotency для retry-sensitive операции;
- optimistic concurrency или immutable snapshot, если они нужны домену;
- отсутствие секретов и пользовательских данных в логах;
- migration forward/backward либо документированный restore plan.

Frontend-цена, permissions и approval никогда не считаются авторитетными без
серверной проверки.

## Render и печать

До утверждения production render требуются:

- утверждённый `PrintProfile` и версия renderer;
- детерминированный fixture и golden PDF;
- проверка trim, bleed, safe zone, spine и layflat geometry;
- встраивание шрифтов, ожидаемый color pipeline и размеры изображений;
- закрытое хранение артефакта и retry без потери approval;
- физическая контрольная печать и подписанный production gate.

Красивое browser preview не доказывает готовность файла к печати.

## Причины не принимать результат

- обязательная проверка не запускалась или её результат выдуман;
- acceptance criteria изменены постфактум под реализацию;
- diff содержит несвязанный scope или скрытую смену архитектуры;
- production-функция подменена недокументированным mock/placeholder;
- сервер доверяет цене, ownership или approval из frontend;
- работа пользователя теряется при ожидаемой восстанавливаемой ошибке;
- открытое бизнес-решение было угадано;
- reviewer нашёл незакрытую критичную проблему;
- результат нельзя воспроизвести описанными командами.

Замечания возвращаются исполнителю с точным сценарием воспроизведения,
ожидаемым и фактическим результатом. Исправление должно быть узким; критерии
приёмки не переписываются, чтобы скрыть несоответствие.
