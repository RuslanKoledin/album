## 1. Назначение документа

Этот файл подробно описывает frontend-возможности и технические критерии.
Фактический порядок delivery, вертикальные срезы и business/print gates задаёт
`roadmap.md`. Обязательные инженерные правила находятся только в
`../engineering/frontend.md`.

P0–P14 больше не являются календарными этапами, которые нужно полностью пройти
сверху вниз. Это нумерованный backlog. Для текущего milestone берётся только
минимально необходимая часть соответствующих P-разделов. Реальный backend
подключается contract-группами сразу после готовности, а не после завершения
всей mock-версии.

Главная цель первого большого релиза:

> Пользователь без AI выбирает готовый продукт и шаблон, загружает фотографии,
> редактирует ограниченную печатную фотокнигу, утверждает макет, оформляет заказ
> и видит его статус.

Это не план редактора уровня Canva. Конструктор работает с заранее
подготовленными темами, шаблонами, макетами и допустимыми настройками.

## 2. Продуктовые границы backlog

- Только адаптивный веб-сайт; без мобильного приложения и Telegram-бота.
- Сначала полностью работоспособный ограниченный ручной конструктор; AI только
  после production-gate.
- Календари, открытки, школьные и корпоративные задачи в MVP принимаются через
  индивидуальную заявку. Отдельные конструкторы для них пока не создаются.
- Отдельного публичного раздела и кабинета фотографа в MVP нет.
- Категория проекта помогает рекомендовать шаблоны, но ничего не запрещает.
- Пустой свободный холст и редактор уровня Canva не входят в scope.

## 3. Как использовать backlog

Порядок чтения, архитектура, testing и Definition of Done определены в

## 4. Mock-first стратегия

### 4.1. Что означает «работаем с моками»

Frontend использует те же URL, DTO, RTK Query endpoints, состояния загрузки и
ошибки, которые позднее будут использоваться с backend. Ответы временно
возвращает Mock Service Worker (MSW).

MSW добавляется только при реализации первого backend-зависимого модуля. До
этого доменное ядро тестируется обычными TypeScript fixtures без сетевого слоя.

### 4.2. Правила моков

- Страницы не импортируют fixtures напрямую.
- UI получает удалённые данные только через публичный API своего модуля.
- RTK Query endpoints не знают, отвечает MSW или настоящий backend.
- Моки каждого домена находятся рядом с доменом:
  `modules/<module>/mocks`.
- `app` только запускает mock worker и собирает handlers модулей.
- Моки включаются переменной `VITE_ENABLE_MOCKS=true` и динамическим импортом,
  поэтому не попадают в production-путь при выключенном режиме.
- Fixtures типизированы теми же DTO, что и endpoint.
- У каждого важного запроса есть успешный ответ, ожидаемая ошибка и задержка.
- Тесты могут переопределять handler для конкретного сценария.
- `File`, `Blob` и object URL не хранятся в Redux.
- Для выбранных пользователем файлов используется реестр модуля загрузки.
- На mock-этапе JSON-состояние проекта можно сохранять локально. Реальное
  восстановление оригиналов после закрытия браузера считается готовым только
  после подключения объектного хранилища и подписанных URL.

### 4.3. Предлагаемая структура моков

```text
src/
  app/
    mocks/
      browser.ts
      handlers.ts
      startMocking.ts
  modules/
    catalog/
      api/
      mocks/
    project/
      api/
      mocks/
    auth/
      api/
      mocks/
  tests/
    mocks/
      server.ts
```

Папки создаются по мере появления реального модуля, а не заранее.

### 4.4. Параллельная работа с backend

Backend развивается одновременно по `../engineering/backend.md`, а порядок
общих milestone задан `roadmap.md`.

Для каждой backend-зависимой функции порядок обязательный:

1. Согласовать endpoint, DTO, статусы, права, ошибки, retry и idempotency.
2. Зафиксировать контракт в OpenAPI/JSON Schema и добавить examples.
3. Создать frontend-типы, RTK Query endpoint и MSW handler по контракту.
4. Передать тот же контракт backend-команде.
5. Backend реализует endpoint и contract tests параллельно с frontend UI.
6. После готовности backend выключить моки и пройти интеграционный сценарий.

Статусы contract-группы: `DRAFT` → `FROZEN` → `BACKEND_READY` и
`FRONTEND_READY` → `INTEGRATED`. Mock handler не является отдельной спецификацией
и не может расходиться с backend.

### Не считать готовым

- Публичные страницы пока являются ранним честным срезом, а не финальным
  маркетинговым сайтом: нет реальных фотографий продукта, подтверждённых цен,
  сроков и производственных характеристик.
- `/create` подключён к real backend/MinIO для JPEG/PNG, но checkout и order
  остаются mock-only без оплаты и производственных обещаний.
- В `/account` проекты читаются из backend при отключённых моках; заказы
  остаются MSW-only, юридических маршрутов ещё нет.
- Редактор покрывает ограниченный ручной P5-срез, real asset read/reload и
  authoritative server preflight/approval, но ещё не имеет generated
  thumbnails и print PDF.
- Нет настоящих размеров, цен и производственных допусков.
- Backend B1–B4 preflight/approval implementation и technical evidence созданы;
  pre-M0 render HTTP gate исполняется без создания job; formal named-owner
  acceptance, production providers/origins и настоящий print-render B4
  остаются открыты.

## 6. Roadmap

### P0. Входные данные производства — параллельный business/print-трек

Frontend может начать работу с явно помеченными mock-значениями, но нельзя
считать печатный валидатор и цену production-ready без этих данных.

- [ ] Выбрать один референсный продукт для первого end-to-end пути.
- [ ] Зафиксировать размеры и правила референсного продукта.
- [ ] Провести контрольную печать до полного редактора.
- [ ] Второй продукт проверять отдельным повтором этого gate после первой alpha.
- [ ] Получить вылеты, безопасные зоны и линию сгиба.
- [ ] Получить минимальное разрешение фотографий и правила DPI.
- [ ] Получить минимальное и максимальное число разворотов.
- [ ] Получить ограничения текста, обложки и корешка.
- [ ] Получить базовые цены, цену разворота, коробки и доставки.

**Результат первого gate:** одна утверждённая производственная спецификация,
контрольная печать и provisional unit economics. До этого значения в приложении
обязательно обозначаются как тестовые.

## 7. Что сознательно не делаем сейчас

- AI-чат, LLM API, локальные модели и prompt engineering.
- Пустой свободный холст и произвольные координаты элементов.
- Совместное редактирование в реальном времени.
- Marketplace шаблонов.
- Отдельный кабинет фотографа.
- Конструкторы календарей, открыток и школьных предзаказов.
- Автоматическую ERP и прямое управление печатным оборудованием.
- Новую библиотеку состояния, запросов, роутинга или UI kit.
- Оптимизацию и memoization без измеренной проблемы.

## 9. Текущая точка продолжения

Текущие активные milestone: **M0, пользовательский gate M2 и print-render часть
backend B4** из integrated roadmap. Technical evidence B1–B4 для замороженных
auth/project/upload/preflight/approval контрактов собрано; formal named-owner
acceptance продолжается параллельно.

Исполнимые протоколы M0 и M2 собраны в `../gates/`: для M0 дополнительно готов
shortlist печатных партнёров Бишкека и единый технический опросник. Backend
acceptance record добавлен в `../api/backend-handoff.md`. Документы готовы к
передаче ответственным, но не считаются результатом проверки без заполненного
evidence и подписи владельца.

Research M0 зафиксировал ELQR/manual confirmation как alpha payment path и
SMSPro/NIKITA как первый OTP-кандидат для пилота. Backend stack, local
PostgreSQL/MinIO и B1–B4 evidence описаны в `../engineering/backend-stack.md` и
backend ADR; это не заменяет provider contracts или formal backend acceptance.

Следующая точка:

> print-render по подготовленному DRAFT lifecycle: immutable print profile,
> golden PDF, закрытое хранение и retry без потери approval.
> Authoritative preflight/approval и upload/asset slice уже проходят real
> backend no-mock flow; actual database session expiry возвращает отдельный
> `SESSION_EXPIRED`, а редактор сохраняет draft и ведёт на повторный вход.
> Pre-M0 render endpoint уже проверяет session/CSRF, ownership и свежесть
> approval: возвращает profile gate или `APPROVAL_OUTDATED`, но намеренно не

> Immutable `PrintProfileV1` и его content-derived version уже реализованы, но
> production instance остаётся невозможным без заполненной M0-техкарты и

Параллельный публичный P9-срез больше не содержит пустую `/help`: страница
объясняет фактический тестовый путь, ограничения JPEG/PNG, предварительную
проверку, отсутствие настоящей оплаты и необходимость privacy/production gates.
`robots.txt` разрешает публичные страницы и исключает служебные SPA-маршруты;
sitemap намеренно не публикуется без подтверждённого домена.

P4, P5, P6.1, P6.2, P7 и walking-skeleton часть P8/P10 завершены. `/create`
ведёт через формат, стиль,
комплектацию и seeded photo set на одном route; выбранное состояние переживает
navigation/reload, а единственные допустимые формат и шаблон выбираются
автоматически без пустого обязательного клика. Тестовая цена рассчитывается
одинаково в конфигураторе, checkout и заказе и явно не выдаётся за production
quote. Перед
фото и созданием проекта работает session gate с безопасным возвратом в тот же
URL. Непустой проект создаётся через замороженный `POST /projects` и открывается
в редакторе. Локальная очередь принимает и проверяет несколько JPEG/PNG,
показывает preview, progress, cancel и retry. Mock signed upload резервирует
asset ID, обновляет истёкшую инструкцию без потери оригинала, подтверждает
загрузку и сохраняет uploaded references в новой project revision.
Project asset list, status, temporary private preview и trusted dimensions
работают и с real backend/MinIO; редактор после reload использует обновлённую
signed GET URL. Actual session expiry сохраняет локальный editor draft,
возвращает пользователя через login в тот же проект и автоматически возобновляет
autosave. Generated thumbnails и retention остаются следующими media-hardening
задачами. Phone OTP нормализует локальный
номер в E.164, обрабатывает безопасные ошибки, показывает mock-код только в
development и возвращает пользователя только на внутренний безопасный route.
Session bootstrap и logout работают через RTK Query/MSW; публичные страницы и
настройки книги остаются доступными гостю. Auth UI проверен на 390, 768 и 1440
px. Навигация редактора
поддерживает добавление,
перестановку, безопасное удаление и предупреждения на миниатюрах. Photo flow
покрывает фильтрацию, назначение, замену, удаление, явный swap, zoom/focal point
и неблокирующее предупреждение качества. Совместимые макеты меняются одной
обратимой командой с сохранением подходящих фото. Текстовые поля ограничены
печатными настройками каталога и обнаруживают переполнение до команды. Фон и
палитра показываются как единое ограниченное оформление книги. Все durable-изменения проходят через
существующие `BookCommand`, undo/redo и autosave. Сценарий проверен в браузере
на 390, 768 и 1440 px без console errors.
Desktop и mobile состояния ранее сохранены в
[Figma — Photobook Editor](https://www.figma.com/design/1RuLKi3o6uHEjtNOmwMGn3)
как необязательный визуальный референс. Дальнейшая разработка по умолчанию идёт
code-first с проверкой в браузере; обновление Figma не является gate.

Account показывает URL-backed вкладки проектов, заказов и профиля, а DRAFT
cursor-list contracts позволяют backend реализовать те же read models без
изменения page API. После mock checkout заказ открывается и из account.
Карточки проектов используют `coverPreviewUrl`, сохраняют изменённое в редакторе
название и явно предлагают изменить уже утверждённый макет. Checkout показывает
текущий способ получения и адрес; preview перечисляет локальные рекомендации по
конкретным поверхностям рядом с книгой на desktop.
Внутренний `/operator/orders/:orderId` читает только admin detail: клиент,
утверждённую revision и связанный preflight snapshot. Публичной ссылки, fake
payment, fake print PDF и производственных mutations нет.
Account проверен на 390, 768 и 1440 px; заполненный список заказов на 390 px не
создаёт горизонтальный scroll и сохраняет минимальные touch-targets 44 px.

Повторный usability-аудит полного mock-пути устранён: публичные страницы
различают demo-расчёт и неподтверждённую production-цену; категории больше не
обещают персонализацию при одном шаблоне; preview использует реальные диапазоны
страниц и показывает содержание поздней preflight-рекомендации до согласия.
Утверждение честно фиксирует revision только для тестовой заявки. Login сохраняет
активную вкладку account, заказы показывают связанный проект, номера КР имеют
читаемый формат, а мобильная публичная шапка оставляет доступ к проектам. Основные
маршруты повторно проверены на 390, 768 и 1440 px без горизонтального overflow;
offline-состояние редактора обнаруживается и снимается после восстановления
сети.

Следующая P3/P8-вертикаль также закрыла локальную формулу цены. Configurator и
checkout получают provisional calculation через RTK Query/MSW; loading,
recoverable error и retry сохраняют выбранную комплектацию. Mock order принимает
только quote, совпадающий с утверждённым документом и способом получения.

Первая HTTP-группа заморожена внутренним решением Product Owner и реализована на

заменяет backend acceptance до `BACKEND_READY`.

Backend B0, production discovery M0 и backend review схем P1/P2/OpenAPI
выполняются параллельно. После `BACKEND_READY` первая contract-группа
