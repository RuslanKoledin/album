# ADR 0004: Direct asset upload and private previews

- Status: provisional accepted
- Date: 23 July 2026
- Scope: B3 JPEG/PNG asset lifecycle

## Decision

The browser uploads JPEG and PNG originals directly to the private
S3-compatible bucket. The API first reserves stable asset records and returns
short-lived signed `PUT` instructions. Every object key is generated by the
backend and scoped to one project and asset:
`projects/{projectId}/assets/{assetId}/original`.

Upload-batch idempotency is scoped to the owner and project. An identical retry
returns the original batch, asset identities and instructions; reuse with
different metadata returns the frozen conflict envelope.

Completion never trusts the browser alone. The API checks object existence,
reserved byte size, media type and normalized storage ETag before changing the
asset state. Repeating completion with the same accepted metadata is
idempotent. Renewing an instruction preserves the asset, client-file and object
identities and is rejected after completion.

## Media metadata and previews

For the first B3 slice, the API reads a bounded prefix of the stored original
and parses JPEG/PNG headers to derive trusted pixel dimensions. A successfully
parsed image becomes `ready`; a received image that needs later processing
remains `uploaded`.

The temporary `thumbnailUrl` is currently a signed private GET of the original.
This is an explicit integration bridge, not a generated thumbnail. A bounded
thumbnail worker, derivative object key and failure/retry state remain separate
work. `BookDocumentV1` stores only the stable `assetId`; expiring URLs and media
metadata stay in the asset read model.

## Security and ownership

- Asset reads and mutations are scoped by session owner, project and asset.
- Missing and foreign identifiers use the same safe `404`.
- Mutations require the existing CSRF protection.
- A document revision cannot reference a foreign, missing or incomplete
  non-fixture asset.
- Signed URLs are short-lived and authorize only one object key and operation.
- Local MinIO CORS is infrastructure configuration. Production bucket CORS,
  storage provider, retention and data residency remain deployment gates.

## Evidence

- The disposable-database HTTP integration flow proves upload-batch
  idempotency/conflict, an actually expired signed URL, renew, direct MinIO PUT,
  ETag/size/media verification, completion replay, trusted PNG dimensions,
  private preview read and rejection of a missing document asset.
- A real browser with frontend mocks disabled completed login, project
  creation, direct JPEG upload, document save, editor assignment and reload.
  MinIO returned the completion ETag through CORS and the refreshed private
  preview loaded without console errors.

## Deferred

- Generated thumbnails and asynchronous media processing.
- HEIC/HEIF support and EXIF orientation normalization.
- Asset deletion, retention cleanup and orphan reconciliation.
- Antivirus/content scanning and authoritative server-side SHA-256.
- Production object storage, CDN and privacy/retention decisions.
