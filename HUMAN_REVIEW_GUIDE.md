# Руководство владельцев по приёмке задач Codex

Вы не обязаны уметь писать код, но должны требовать проверяемые доказательства.

## 1. Что Codex обязан показать

Для каждой задачи:

- ссылку на task-файл;
- краткое описание результата;
- список изменённых файлов;
- diff;
- точные команды тестов;
- exit code каждой команды;
- screenshots/video/PDF для визуального функционала;
- список ручных шагов;
- известные ограничения;
- статус только `IMPLEMENTED`.

Фраза «всё готово» без evidence не принимается.

## 2. Минимальная ручная проверка

Один из владельцев:

1. Запускает приложение по README.
2. Проходит основной сценарий задачи.
3. Намеренно вводит неправильные данные.
4. Проверяет повторный клик, refresh и back.
5. Проверяет мобильный viewport, если задача касается UI.
6. Проверяет, что соседняя функция не сломалась.
7. Просматривает review report независимого Codex.

Второй владелец подтверждает наиболее рискованные задачи: авторизация, загрузка, BookDocument, renderer, цена, оплата, approval, admin и производство.

## 3. Красные флаги

Не ставьте `VERIFIED`, если:

- тесты не запускались;
- тесты skipped или удалены;
- Codex изменил acceptance criteria после реализации;
- в diff есть несвязанные изменения;
- появились `TODO`, mock, placeholder или hardcoded value;
- сервер доверяет цене или правам из frontend;
- миграция не проверена;
- UI работает только в happy path;
- задача зависит от открытого TBD;
- Codex изменил `MASTER_SPEC.md`;
- Reviewer Codex нашёл Critical/Major проблему;
- результат нельзя воспроизвести вашей командой.

## 4. Как принимать UI

Попросите Builder Codex предоставить:

- desktop screenshot;
- mobile screenshot;
- loading state;
- empty state;
- validation error;
- server error;
- disabled state;
- success state.

Проверьте тексты, навигацию, кнопки, сохранение и возврат назад.

## 5. Как принимать API и backend без глубокого знания кода

Требуйте:

- OpenAPI или понятный контракт request/response;
- пример успешного запроса;
- пример ошибки;
- тест чужого пользователя/объекта;
- тест повторного запроса;
- тест некорректных данных;
- proof, что цена/роль/статус проверяются сервером;
- database migration evidence.

## 6. Как принимать платежи и заказы

Обязательно проверить:

- двойной клик не создаёт два заказа;
- повторный webhook не начисляет оплату дважды;
- неправильная подпись webhook отклоняется;
- сумма оплаты сопоставляется с заказом;
- unpaid заказ не уходит в производство;
- возврат не превышает оплату;
- approved version и price snapshot неизменяемы.

## 7. Как принимать renderer

Требуйте:

- одинаковый fixture BookDocument;
- browser screenshot;
- generated PDF;
- автоматический parity report;
- подтверждение типографии для тестового PDF;
- hash и renderer version;
- проверку fonts, crop, bleed, safe zone и gutter.

## 8. Как принимать безопасность

Попросите Reviewer Codex отдельно проверить:

- доступ к чужому project ID;
- доступ к чужой signed URL;
- admin endpoint обычным пользователем;
- brute force OTP;
- file type spoofing;
- secrets в repo и logs;
- повтор webhook;
- удаление/скачивание чужих фотографий.

## 9. Финальное решение

- `IMPLEMENTED`: Codex закончил и предоставил evidence.
- `VERIFIED`: вы воспроизвели результат, review не содержит блокеров.
- `DONE`: изменения merged, CI зелёный, документация обновлена.

Никогда не ставьте `DONE` автоматически по финальному сообщению агента.
